# Craft Anything tool catalog

Generated from the live MCP server (`craft-anything-cli mcp --all-tools --deep`, tools/list), `craft-anything-cli commands` and `craft-anything-cli capabilities` (Craft Anything 0.3.0, macOS arm64; 315 tools in 17 toolsets). Every tool is an MCP tool (Hermes: `mcp_craft-anything_<tool>`) and a CLI command (`craft-anything-cli <tool with dashes> --json '{...}'`). Grep this file rather than reading it whole.

Marks: `[listed]` = in the default tool list (Clean room, Essentials; 29 tools incl. `list_toolsets`/`enable_toolset`). `[clean]` = allowed in Clean room (the default mode); no mark = needs Deep mode (`--deep`, or `settings_set deep_mode true`), refused otherwise with `This looks inside the original (its code, files or page source), which Clean room never does.` `[ro]` = read-only. `[!]` = destructive hint: may discard data, run code or change a device; the ones that run code or change a device return `consent_required` unless the server runs with `--allow-run` (or the setting `ask_before_running` is false). `[target]` = needs an open target (`core_target_open`). `?` = optional, `a|b` = choices, `=x` = default. Calling a tool from a toolset that isn't enabled enables it.

Toolsets: `core` Essentials (35), `native` Programs (native code) (55), `apple` Apple apps (14), `formats` File formats (36), `managed` .NET apps (8), `android` Android apps (14), `java` Java programs (6), `adb` Connected phone (24), `browser` Websites (22), `javascript` Electron and JavaScript (11), `runtime` Running programs (14), `frida` Frida instrumentation (9), `application` Comparing and rebuilding (17), `database` Databases (1), `projects` Projects (27), `setup` Engines and settings (16), `build` Building (6)

- `core_unknowns_show` (Open questions) [listed] [clean] [ro]: {domain?, severity?: low|medium|high|critical, status?: open|investigating|blocked|contradicted|resolved} — Recorded unknowns, filtered by status, severity or domain.
- `core_unknown_add` (Record an open question) [listed] [clean]: {domain? ="general", evidence_against?, evidence_for?, probes?, question, severity?: low|medium|high|critical} — Record something not yet known, with what would settle it.
- `core_unknown_edit` (Update an open question) [listed] [clean]: {based_on_revision, evidence_against?, evidence_for?, probes?, resolution?, severity?: low|medium|high|critical, status?: open|investigating|blocked|contradicted|resolved, unknown_id} — Change an unknown's status, evidence or resolution. Pass based_on_revision; a stale revision gives stale_revision.

- `core_archive_show` (Inventory an archive or app bundle): {if_tampered?: fail|continue, limit? =500, max_depth? =3, max_entries? =200000, max_total_bytes? =4294967296, offset? =0, path?} — Content-addressed inventory of a ZIP/APK/IPA/JAR, Electron ASAR, app bundle or folder: every file with size, kind, role and sha256; nested archives opened to a bounded depth; ASAR integrity hashes and ZIP CRCs checked. Paged (offset/limit).

Bounded size and count; entries that would escape the folder are refused.
- `core_archives_compare` (Compare two artifacts): {left, max_rows? =500, right} — Compare two archives, app bundles or folders file by file: added, removed, changed (by sha256) and moved files. Inputs are absolute paths or core_archive_show evidence.
- `core_person_ask` (Ask the person) [listed] [clean]: {allow_text? =true, choices?, context?, question} — Ask the person a question in the app and wait for the answer: a short question, up to six suggested answers shown as buttons, and optionally a typed reply. Use it when a choice changes the result (scope, style, which feature first) and you can't decide from the evidence. Returns the answer text, or a note to continue with your best judgement if nobody answers within 30 minutes.
- `core_action_approve` (Approve an agent action) [listed] [clean]: {input?, tool_name, tool_use_id?} — Permission check for a coding agent's action (tool name and input). Edits inside the workspace's app folder and common build commands are allowed; dev servers are refused with a hint; anything else asks the person. Returns {behavior: allow, updatedInput} or {behavior: deny, message}.
- `assets_image_generate` (Generate a picture) [listed] [clean]: {prompt, save_as, shape?} — Make a picture with fal.ai (Nano Banana Pro) and save it as a PNG inside app/: a texture, a sky or background, an icon, a title screen or concept art. shape: square (1024x1024, default), wide (1024x576) or tall (576x1024). Costs about $0.15, counted against the project's asset budget. Describe original designs in the original's style; never ask for recognisable characters, logos or brand artwork. Returns where it was saved, the cost and the budget left.
- `assets_model_generate` (Generate a 3D model) [listed] [clean]: {faces?, image?, prompt?, save_as, textured?} — Make a game-ready, low-poly 3D model (GLB) with fal.ai (Tripo P1) and save it inside app/. Give a prompt (a picture is made first, then turned into the model) or an image (a web address, or a picture inside the project such as reference/picture-1.png). faces caps the face count (48 to 20000, default 3000): about 500-1500 for small props and pickups, 2000-5000 for weapons, furniture and vehicles, 6000-15000 for main characters; fewer faces run faster, so use the fewest that still look right. textured (default true) gives colours and surfaces. A textured model costs $0.50 plus $0.15 for the picture, counted against the project's asset budget; it takes a minute or two. Describe one original object per model; never ask for recognisable characters, logos or brand artwork. Returns where it was saved, the cost and the budget left.
- `core_investigation_show` (Investigation so far) [listed] [clean] [ro]: {} — The working memory of this investigation: brief, plan with step status, hypotheses, findings (with evidence ids) and the latest handoff. Read it first when starting or resuming.
- `core_brief_write` (Write the brief) [listed] [clean]: {constraints?, done_when?, purpose?, question, targets?} — Set the investigation brief: the question, purpose, targets, constraints and what 'done' means. Write it before the first analysis call on a new question.
- `core_plan_update` (Update the plan) [listed] [clean]: {based_on_revision?, steps} — Replace the plan with a numbered list of steps, each todo/doing/done/blocked with a short why. Pass based_on_revision to avoid overwriting someone else's update.
- `core_hypothesis_record` (Record a hypothesis) [listed] [clean]: {claim, evidence_against?, evidence_for?, prediction?} — Record a claim being tested, ideally with the prediction that would confirm or refute it, plus any supporting/contradicting evidence ids.
- `core_hypothesis_update` (Update a hypothesis) [listed] [clean]: {add_contradicting_evidence_ids?, add_supporting_evidence_ids?, hypothesis_id, note?, status?: testing|supported|refuted|abandoned} — Change a hypothesis's status (testing/supported/refuted/abandoned) and attach supporting or contradicting evidence ids and notes.
- `core_finding_record` (Record a finding) [listed] [clean]: {confidence?: observed|derived|inferred, evidence_ids, statement} — Record a settled answer. Requires at least one evidence id; every id is checked against the ledger. Findings are the source for reports.
- `core_handoff_write` (Write the handoff) [listed] [clean]: {text} — Rewrite the handoff note: where we are, what's next, traps to avoid. Write it at the end of every turn so the next turn (or agent) resumes without re-deriving.
- `core_journal_read` (Read the journal) [listed] [clean] [ro]: {day?, kind?, limit?, offset? =0, tool?} — Page through the project's append-only journal (tool calls, model turns, consents, errors), filtered by day, kind or tool. Needs an open project.
- `core_report_save` (Save a report) [listed] [clean]: {path, text} — Save a report a client composed (Markdown, HTML or plain text) to an absolute path the person chose. Only .md, .html, .htm or .txt files.
- `core_report_write` (Write a readable report) [listed] [clean]: {format?: markdown|html ="markdown", include_evidence? =true, path?} — Turn the investigation (brief, plan, findings, hypotheses, handoff) and the evidence ledger into a readable report: what we looked at, what we found (each finding with its plain-English summary, confidence and cited evidence), open questions, and how it was done. format=markdown (default) or html. With an absolute path it writes the file (WRITES_FILESYSTEM); otherwise it returns the text.
- `core_overview_show` (Overview) [target]: {detail?: complete|summary ="complete", document?} — One-page summary of a program: format, architecture, entry, segments, counts of functions/strings/imports/exports, libraries, hardening, toolchain hints. detail=summary keeps the full record and returns counts plus a reference to page with core_evidence_browse.
- `native_function_study` (Function dossier) [target]: {detail?: complete|summary ="complete", document?, function} — Everything about one function in one record: facts, pseudo-C, assembly, basic blocks, callers, callees, references, strings, unresolved calls, API boundary and register value flow. Page through big facets with core_evidence_browse; detail=summary returns counts plus a reference first.
- `core_feature_find` (Trace a feature) [target]: {case_sensitive? =false, document?, query} — Literal text → matching strings, functions and imports → the code that uses them → the functions involved.
- `core_target_triage` (What is this?): {path?} — Say what a file is in plain English (format, OS, architecture, language/toolchain hints such as Go, Rust, .NET, Electron, Flutter, Delphi, packers) and which toolsets and tools to use next. Uses the active target unless path is given.
- `core_evidence_browse` (Page through evidence) [listed] [clean]: {show: {kind: summary|part|row|rows|function-part, …}, source: {kind: saved|inline, …}} — View part of a stored (or inline) evidence record: the summary, one part, one row of a list, a page of a list's rows (optionally only the rows matching given field values, cut to chosen fields, with the field names listed), or a part of a function dossier (pseudocode, assembly, basic_blocks, callers, callees, flow_*…), with coverage and next_offset. Nothing is analysed again.
- `rebuild_check` (Check my build) [listed] [clean]: {project?, wait_minutes? =20} — For the builder: test the project's current build against the original now, with the same checks Craft Anything runs after each turn (a website's likeness at each width with the padding, colour, font and layout differences; an app's or game's picture against the original's; whether it builds; the mechanics sheet; credits). The project's running build answers it, so the builder can fix what it lists and check again before replying. Not counted as a round. project defaults to the project this tool server works for.

- `app_builds_line_up` (Match functions between two builds): {detail?: complete|summary ="complete", left, limit? =200, max_file_bytes? =536870912, offset? =0, right, show?: all|pairs|changed|ambiguous|only_left|only_right ="all"} — Pair the functions of two builds of a program (two absolute paths) with the built-in engine. - `native_cutter_sessions_list` (List shared Cutter sessions): {ports?} — Find Cutter (or Rizin) sessions shared on this computer: each port given (default 9090) is asked what it has open (file, format, architecture). A session is shared by running `=h& 9090` in Cutter's console; nothing else is reachable.
- `native_cutter_command_run` (Cutter command): {command, limit? =2000, offset? =0, port? =9090} — Run one read-only Rizin command in a shared Cutter session (port, default 9090) and return its text, paged by lines: information (i…), printing and disassembly (p…, x…), analysis (a…), search (/…), seek (s…), flags (f…), comments (C…), types (t…) and help (?…). Ledger status: ready, open, failing or unclear.

- `apple_app_graph_build` (Map an Apple app): {inventory?, path?} — Project an iOS/macOS app's inventory (core_archive_show evidence or a path) into an application graph: bundles and extensions, executables, frameworks, dylibs, signing material, interface files, asset catalogs and embedded runtimes (Flutter, React Native, Electron, Unity…). Runtime hints are inferred from file names.
- `harmony_app_graph_build` (Map a HarmonyOS app): {inventory?, path?} — Project a HarmonyOS package's inventory (core_archive_show evidence or a path) into an application graph: module manifests, HAP/HSP packages, Ark bytecode, native libraries by ABI and resources.
